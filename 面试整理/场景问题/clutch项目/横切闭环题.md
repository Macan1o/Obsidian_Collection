## 一、产品定位与动机

### 为什么要做这样一个产品？

是这样的，我在公司负责应用从零到一落地：产品给名称，我这边要交付。因为有一些限制因素，所以一开始选择跟 AI 一步步聊，质量不稳定；后来选择出高效的提示词把流程沉淀成 Skill，并不断优化，形成多链路节点监督机制

```
规则与红线确认机制
功能选型
出设计稿
形成视觉资产
按稿还原
粘性打磨「间距呼吸感、或者一些简单动效」
```


经过这套流程过后我发现最后质量相对来说比较容易把控。输出结构比较统一。并且后续如果增加节点的话也方便配置。也便于后期维护。

后来就是既然节点链路的话我觉得可以打造一个多Agent工作流，刚开始是打算用n8n的，后来发现n8n它能跑节点，但执行黑盒，人工随时叫停也不顺手。于是我就打造了一个基于LangGraph的多 Agent 编排与监督控制台。状态可看、审批可拦、输出可控。便于不断优化调整，并且减少开发难度，可以根据多样化的节点配置完成需求的多样化


## 二、技术选型与竞品对比

### 为什么选用 LangGraph

我们之所以选择LangGraph是工作流运行时需要一个可靠的状态机。多 Agent SOP 不是线性脚本：有分支、有自动检查、有人工门控。尤其是人审节点，图必须能 interrupt 挂起、等人决策后再 resume——这正好是 LangGraph 的强项；再加上 checkpoint，本地长跑可恢复。因此决定选用现有成熟的LangGraph框架

### 为什么不选择更加成熟的n8n？

如果只是单纯执行脚本把表单、数据库、通知串起来，我会用n8n，没必要自研。n8n虽然也能跑节点，但执行黑盒，人工审核叫停挂起功能也不是很流畅。结合业务我需要每个节点输出人为审核 HITL 精确挂起续跑，避免各节点输出黑盒并且在本地工作区里写代码、改文件、跑 CLI、互相交接。因此决定自己基于LangGraph封装多 Agent 编排与监督应用

```
n8n 自动化的是系统之间的数据；我们自动化并监督的是 Agent 的业务处理。
```


### 有没有了解过 LangSmith / LangFuse ？

> 上面两者是观测层，主要是给 LLM 应用做追踪、评测、成本分析的可观测平台。而我的项目是实际应用层

并且功能逻辑不同，LangSmith、LangFuse 主要给链路打 trace、看 span、比 prompt、做评测，多数挂在应用外面，帮研发「看见模型怎么跑」，不负责一些像零代码拖 SOP，调度人审闸门的功能逻辑。结合其观测层的属性，若以后要做更细的 prompt/token 分析，可以把 Clutch 的 run 接到它们进行分析


### 和 Dify/Coze 有什么区别？

Dify、Coze 更偏 云端/可托管的 LLM 应用搭建台，无法深度碰文件系统、子进程、长驻 bash PTY，也无法调度成熟的 Claude Code、Codex 这类本地 CLI

## 三、端到端链路

### 一次用户发送消息，端到端怎么走？

Tauri WebView → HTTP/WS → FastAPI →

- if `plain chat`： EngineRouter 选路 → MCP ReAct 或 PTY 或者 云 LLM → 状态 patch 经 WebSocket 推 `ClutchState` → React 三栏投影（Chat / Terminal / Changes）。
	
- if `workflow`：JSON → WorkflowCompiler → LangGraph invoke → 节点内再调同一套 EngineRouter

## 四、核心技术难点

### 最大的技术难点是什么

> 最大的难点不是 API 怎么用，而是如何把几条异构执行链捏成同一套可监督的状态闭环

用户侧是零代码画布和 Chat；后端同时存在 LangGraph 工作流、MCP ReAct 工具循环、Hybrid 长驻 bash/PTY，以及图级人工闸门与工具级审批等不同控制流。每条链的产物形态不同（聊天气泡、终端输出、文件变更、工具步骤、等待人工…），但前端必须只投影同一份运行态契约（`ClutchState`），通过 WebSocket 增量更新，而不能在 React 里另搞一套编排真相。所以难在<mark style="background:#d3f8b6">「多引擎统一调度下的一致性」</mark>，如何保证它们共享同一条 run 生命周期时仍然逻辑自洽、失败可操作。可以拆成四层：


<mark style="background:#d3f8b6">1. 契约与投影 </mark> 
各链副作用（消息、终端、改文件、工具步骤、池状态、等待人工）必须收敛进唯一可投影状态，经 `state_patch` 推给前端，禁止第二套真相 [[「前端」ClutchStore 的状态管理设计]]

<mark style="background:#d3f8b6">2. Hybrid 长驻与边界  </mark>
- 多轮上下文不能每次冷启 subprocess，所以要长驻 PTY；但 PTY 没有自然的 turn 结束，要用 marker 轮询切边界，再配合 CLI `--resume` 延续会话。
	
- 池化后还有同工作区并发互锁，因此需要 workspace 锁与 LRU；池满则全局排队，而不是丢消息。

<mark style="background:#d3f8b6">3. 策略路由与解包处理  </mark>  [[策略路由与解包处理]]
用 ProviderSpec / 运行策略把 MCP、PTY、云 LLM 收成少数出口；返回值强制解包，避免契约漂移直接打进 Chat。

<mark style="background:#d3f8b6">4. 双层 HITL 与恢复 </mark> 
- 图级 interrupt/checkpoint 与工具级风险闸门并存：状态必须和 WebSocket 投影对齐，决策用完即清。[[图级和工具级HITL以及Check节点]]
	
- checkpoint / 落盘与重读策略，保证暂停续跑、进程恢复后监督面仍一致。

## 五、技术栈与职责

### 用了哪些技术栈，各自职责

- Tauri：桌面壳与 Sidecar 生命周期；
	
- React：状态投影与画布；
	
- FastAPI：API/WS的门面，负责鉴权和路由编排； 
	
- LangGraph：唯一编排引擎SSOT，负责节点、边的编排，保证状态一致性；
	
- WebSocket：增量 `state_patch`，负责增量的推送；
	
- Rust： 偏宿主能力，负责窗口、系统能力「选文件夹、打开路径」，注入进程Token

## 六、复盘与改进

### 如果需要对项目进行优化，你会改什么

- 多Agent节点的输出内容拼接策略 compact 处理「目前上下节点的输出还是通过全量拼接的方式进行的，如果十几个节点的时候可能会出现细节丢失情况，后续需要对其压缩」；
	
- 编译器对并行 fan-out 的可观测性加强「目前单节点是可以并行多节点，但是状态没有对多节点进行显示，这个后期也是需要对齐优化的」；
	
- 风险表可配置化「MCP 风险仍主要靠内置 token 表，误报/漏报都靠改代码。我会把风险策略做成可配置，后续由用户对风险操作进行自主配置」

## 七、产品与协作

### 一个典型的 0→1 落地，从配置到交付大概多久？

一个典型的 0→1 流程是：规则确认 → 功能选型 → 出设计稿 → 视觉资产 → 按稿还原 → 粘性打磨。每个节点对应一个 agent_task，中间有 check 自动校验和 human_gate 人工审批。

配置工作流大概 10 分钟，跑完一条链路交付产品大概 40-60 分钟取决于 LLM 响应速度和人工审批环节，最终交付质量比纯 prompt 对话提升明显——主要体现在输出结构统一、视觉一致性可控、失败可回溯。
