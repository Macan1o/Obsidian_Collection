# 一、核心架构设计

## LangGraph 运转原理和 Workflow 编译器

[[LangGraph运转链路]]

#### 省流版

主要分为编译器和运行器两个时期说明：

编译器主要对节点和边进行编译，节点的话就是通过闭包函数将前端 type 映射到对应节点的执行逻辑，这里为什么要用闭包呢，因为 LangGraph 的回调仅支持 state 到 state 的单餐逻辑，因此需要利用闭包捕获链路固定的 node、workflow 等信息 ，`_run` 闭包函数只接受节点的动态变化状态。相当于一层透传，然后特殊的 human_gate 节点也就是需要人工审核的节点需要进行注册到 LangGraph 中便于利用 interupt_brfore 执行暂停逻辑。

对边的编译主要分为条件边编译和非条件边编译。条件边也就是上游是 check 和 huaman_gate 的节点，需要注册到 LangGraph 的条件边数组中，非条件边注册到非条件数组中，然后将对应节点分支节点注册成 path_map 。根据不同的条件到不同的节点嘛。然后执行期条件边需要利用闭包函数 `_route` 读取编译后的 path_map 来指导 LangGraph 运行。非条件边只需要按节点往下执行即可。

最终收束成 LangGraph 调 `_run` → 根据状态看边 / 问 `_route` → 去下一 id 的运转链路

### 为什么要自研「JSON → LangGraph」编译器，而不是手写图？

- 用户要零代码拖拽 SOP 配置的话，画布产出是 JSON；
	
- LangGraph 要的是可执行 `StateGraph`。中间必须有编译层，把「产品语言的节点/边」翻译成「引擎语言的 handler节点 + 条件边」。手写图无法让非开发用户改流程，也不符合「流程显式可编辑」的产品目标。


### 五类节点分别是什么？为什么这样抽象？

[[LangGraph 、五handler 、_wrap_handler之间的运行关系]]

`start` / `agent_task` / `check` / `human_gate` / `end`。

- start/end：边界与生命周期，负责链路的启动和结束，有完善的生命周期
	
- agent_task：真正干活（调路由后的引擎）
	
- check：校验节点，可以写校验提示词来优化工作流链路
	
- human_gate：人工决策点，根据多节点产出优化工作流链路

这五类覆盖SOP 的核心模式（<mark style="background:#d3f8b6">执行 -- 检查 -- 审批 -- 分支</mark>），更多类型（如 loop、parallel）可以通过复合现有节点 + 条件边实现，避免过早抽象，并且再多类型会让画布认知负担爆炸；再少则无法表达监督。


### 多个 Agent 并行跑的时候状态竞争怎么避免，以及 State 全局管理是怎么做的

> 状态的主键是 `run_id` —— 每个会话 / 每次运行一份 `ClutchState`。所谓「全局」，指的是这一次 run 的唯一真相

工作流里多个 Agent 节点，多数时候是 LangGraph 按图串行推进：

当前只有一个 `active_node_id` / `active_agent`，跑完再路由下一跳，天然减少同图内写状态打架。

跨会话并行时，多个 `run_id` 各跑各的，根据不同的 `run_id` 存储：内存 `_run_states[run_id]`，磁盘 `states/{run_id}.json`，WebSocket 按 `run_id` 订阅；前端 `clutchStore` 收到 patch 时 `run_id` 对不上直接丢掉。

真正容易撞车的是共享本机资源，用锁和队列挡（同一 workspace 互斥、session 池限制、全局排队池）。状态更新统一 `_merge_patch` → `_commit_run_state`（写内存+落盘）→ `state_patch` 推前端，React 只负责投影。


### 闭包捕获注入上下文 —— 解决什么问题？

> 这个点主要卡在 LangGraph 的回调签名，LangGraph 节点回调本质上是 `state → state` 单参。


但编译时我们的业务handler是需要知道「当前是哪个画布节点、整张 workflow JSON 是什么」，条件边还要知道「从哪个 source 出发、 path_map 怎么映射」

除`state` 外的另外两个参数在编译期就已经定死了，因此通过包装函数封装闭包函数，此时只需要将改变的 state 参数由 LangGraph 透传给闭包函数即可既不破坏框架约定，业务又能拿到完整上下文。

#### 闭包核心

> 适配单参签名 + 注入执行时仍需要、但 LangGraph 不会传的上下文


### 出边条件一致性强制校验

> 这个主要是由于LangGraph的两种边的编法不同：

- 一种是无条件边，就是无论这个节点执行结束，不管中间产出什么，都固定走到连着的下一个节点；
	
- 一种是条件边，边上带了 `when`，比如 `passed`/`failed`，或 `approve`/`reject`/`retry`。意思是节点跑完会先留下一个分支信号，比如 check 写进 `check_result`，人工闸门留下 `human_decision`，路由再根据这个信号走对应节点

#### 不允许同一个节点既挂一条无条件边，又挂一条条件边。否则编译器没法判断。所以编译期直接抛错拒绝。

编译器编译好的 `path_map` 负责「这个信号对应哪个下游节点」，编译器里 `_route` 调 `route_next` 拿到 branch「`passed / failed` 或 `approve / reject / retry`」后，会先校验这个 branch 在闭包里的 `path_map` 里存在，然后把 branch 返回给 `add_conditional_edges`；LangGraph 再按 `path_map` 映射到具体节点。


> 条件路由的信号从哪来？

上游 `check` / `human_gate` 写入状态里的路由信号（如通过/拒绝/重试），`route_next` 读状态决定下一跳。人审决策要进 checkpoint，用完清空，避免下一个闸门被「上次 Allow」自动放行。

	checkpoint 是 LangGraph 自带的图运行快照，通过 MemorySaver 实现可续跑的 LangGraph 状态快照

## HITL「关键决策点时把控制权交回人」 + MCP 风险闸门

[[图级和工具级HITL以及Check节点]]

#### 省流版

<mark style="background:#d3f8b6">图级</mark>：工作流执行到 human_gate 节点时，运行状态把状态写成 awaiting_human ，LangGraph 在这里挂起，注明 pending 类型，节点暂停，前端弹出审批，用户操作后，Sidecar 带着拿着这次选择 resume ；条件边的 `_route` 根据结果查 path_map ，再跳到对应下一节点，图继续流转

<mark style="background:#d3f8b6">工具级</mark>：ReAct模型里先给出 tool_shell ，Sidecar 检查是否高危（写/删/Shell），若命中且开启了风险暂停，这次工具不执行，将当前上下文存到`mcp_pending` 中，注明 pending 类型，并将当前循环卡在等人审，人点击 Allow 后落盘，然后进行下一轮ReAct，并且执行`pop_pending`，approve 还会记 approval key，防止下一相同调用自动再拦或重复打扰。

<mark style="background:#d3f8b6">check节点</mark>：根据 handler 内部逻辑「LLM」判断 passed / failed 然后继续走条件边的逻辑




### 人工节点挂起与断点续跑怎么实现？

编译时收集所有 `human_gate` id，`graph.compile(checkpointer=MemorySaver(), interrupt_before=human_gate_ids)` 并完成 interrupt 节点注册。当状态跑到人工审批节点前前 interrupt，状态通过`MemorySaver` 进 checkpoint；前端经 WebSocket 看到 `awaiting_human`，用户 Allow/Reject/Retry；后端 `update_state` 写入 `human_decision` 再 resume。  

关键点： 精确续跑靠 `thread_id` 「通过config配置完成与run_id的映射从而精准定位轮次」+ checkpoint，不是重跑整张图；决策消费后要清掉，防串闸。


### 为什么用 MemorySaver？生产会不会丢？

[[文件回滚部署]]

因为它刚好接上 LangGraph 的 interrupt / resume 且延迟低，优先零外部依赖，不引入 Postgres / SQLite checkpointer。

用户可见的会话投影不靠它——`run_state_store` 会把 ClutchState 落到磁盘 JSON，重启后还能 hydrate。丢的只是「同一张已编译图的断点续跑能力」。三层状态的具体职责和择优逻辑见「数据持久化与修复」章节。


### MCP ReAct 的风险分级怎么做？高危如何闸门？

ReAct 循环里每次 tool call 先过风险表：读/搜偏安全，写文件、删、危险 shell 标高危。权限模式（Agent / Ask / Full）决定是否 `pause_on_risky`。高危时不落盘，先推 `human_required`，审批通过才真正执行；同 run 内可对重复审批 key 去重，避免同操作刷屏。  

	闭环话术： 监督不是事后看日志，而是写操作前插入硬闸门。


> 工作流 human_gate 和 MCP 工具审批是不是一回事？

同属 HITL，层级不同：前者是图级业务审批节点；后者是工具级运行时风险门控。图级用 LangGraph interrupt；工具级用 pending approval + 恢复 ReAct 循环。产品上统一成 Allow/Reject/Retry 交互，降低用户心智成本。

	MCP工具审批节点

高危工具执行前，ReAct 先停住，把当时的对话和待调工具存进 `pending`，状态改成等人审。用户点 Allow 后，带着这份旧对话重新进循环，先执行刚批过的工具，再继续往后跑；点 Reject 就清掉 pending、结束本回合。

## 长驻 bash PTY 会话池

### 长驻 bash PTY是怎么实现的？

[[CLI 的 Hybrid 完整链路实现]]

### 为什么要做 PTY 会话池，而不是每次 `subprocess` 起一次 CLI？

每次 `subprocess` 起 CLI 启动开销大，而且进程一结束环境、工作目录和会话上下文就丢了，多轮对话很难真正续上。PTY 会话池按 `run_id` 保活一条 bash，在同一终端里反复跑 CLI，既能复用进程和环境，也方便带 `--resume` 做长会话；同时用池限制并发、空闲回收，并在 Hybrid 失败或不适合时回退 `subprocess` ，兼顾连续性和稳定性。


### 池化复用 / LRU / 工作区互斥——各自防什么？

[[池化复用、LRU、工作区互斥]]

- 池化： 多 Chat session 共享有限 shell 槽位（`CLUTCH_SHELL_MAX_SESSIONS`）
	
- LRU 驱逐： 槽满时踢最久未用，防 shell 开太多占满内存/句柄；池满时优先腾空闲位
	
- 工作区互斥锁： 同目录并发 `claude -p` 会互锁/写乱仓库，所以同 workspace 串行  

池满时新 session 进全局 FIFO（`queued_pool`），而不是直接拒绝——体验上「排队」优于「报错」。



### 会话快照 + `--resume` 怎么配合？

`--resume` 管 CLI 侧逻辑会话：首轮生成并保存 `cli_session_id` 「多轮会话id」，下一轮拼命令时带上 `--resume <id>` 让 Claude 等 Agent 自己接着聊。

会话快照管 Clutch 侧磁盘落入：每轮 Hybrid 成功后把 `run_id`、工作区、`cli_session_id`、任务摘要写到 `shell_snapshots/{run_id}.json`。

bash PTY 活跃时靠 `--resume` 续聊；shell 断了重建时靠 `load_snapshot` + `format_handoff_prefix` 把快照垫进 prompt。

# 错误处理与容灾

## PTY 进程中途挂了怎么恢复？用户正在跑的任务会发生什么？

> 核心在 `ShellSessionManager.get_or_create()` 里

### 存活检测

每次获取会话时会先调 `session.alive()` 做存活检测。这个检测是三级回退的：先查 `master_fd` 是否有效，再查 `subprocess.Popen.poll()`，最后用 `os.kill(pid, 0)` 做信号探测。只要任何一关判定进程已死，就标记为 `DISCONNECTED`，关闭旧会话时写一份快照（`write_snapshot=True`），然后 spawn 新的 PTY。

### 上下文交接及状态显示

关键的设计是**恢复通知 + 上下文交接**。重建后会在 `_recovery_notices` 里标记这个 `run_id`「刚恢复过」，下游引擎通过 `consume_shell_recovery()` 一次性消费这个标志。如果标志为 True 且磁盘上有 `shell_snapshots/{run_id}.json`，就会调 `format_handoff_prefix()` 把任务摘要、待办事项、工作目录拼成一段上下文前缀，垫进新一轮 prompt 里，让新 shell「记得」之前在干什么。

### 用户体验

用户侧的体验是：前端会收到 `shell_session_status = "recovering"` 的 patch，UI 上体现为一条恢复提示日志。任务不会丢——因为 Hybrid 每轮成功后都会更新快照，恢复后从上一轮的成功点继续，而不是从头重跑。

### 极端情况

如果 PTY 是在执行 CLI 命令中途挂的（比如 `claude -p` 被杀了），那这一轮的 turn 会判为失败并抛出 `ShellSessionError`，上层会捕获并推一个失败状态给前端。用户可以重新发送消息，此时会触发重建。


## `ClutchState` 损坏或状态不一致怎么处理？

### 读磁盘JSON的的三道保险「先返回正确的`clutchState`结构」

#### 第 1 层：读坏了返回None

读盘 IO 错（`OSError`）、JSON 语法坏（`JSONDecodeError`）、文件不存在 / 空、解析出来不是对象（比如是数组）直接丢弃文件，上层再用内存或空壳，服务继续活着。

#### 第 2 层：能解析，但字段可能旧/缺 → `_coerce_state` 补齐

盘上的 JSON 可能是几个版本前写的，少了新字段。先拿标准数据结构`initial_state()`，再用备份里有的字段合并进去；缺的字段用默认值，保证结构永远合法。

#### 第 3 层：`run_id` 强制锁回传入值

通过 `state["run_id"] = run_id` 强行赋值兜底，防止文件串了。防止JSON内容被修改等极端情况，通过兜底强赋值进行防御编程

### 状态不一致规则逻辑逻辑「磁盘、内存做比对」

```
磁盘读出来了吗？
  ├─ 没有（None，含坏文件）→ 用内存
  └─ 有 → 谁更「可信」？
        · 磁盘 messages 更多 → 信磁盘
        · 条数一样，磁盘 idle、内存还 running → 信磁盘
        · 否则 → 信内存
```

## WebSocket 断连后前端状态怎么同步回来？有没有重连 + 状态对齐机制？

> 我们没有做自动重连，而是做了一套**断连降级 + 重连合并**的机制。

```
断连 → HTTP 拉后端当前全量 → 暂存并立刻渲染
     → 重连 WS
     → 首包全量 patch 与前端底稿合并一次（reconnectHydrate 用完即弃）
     → 之后增量 patch 正常更新 UI
     → 仍 running 则每 3s HTTP 兜底，直到结束
```

# 并发与性能

## 同一台机器上多个并发 `run_id`，资源怎么分配？有没有做过压测？

### 主要问题

- 同时 创建 太多 PTY
	
- 活着的 shell 太多（内存/FD）
	
- 同一仓库 两个 CLI 同时改文件
	
- 同一会话 连续狂发
	
- 池满时用户体验（硬拒 vs 排队）
	
- 长期空闲占坑

> 资源分配是六层防护：

- **第一层，spawn 信号量**：`_spawn_gate = Semaphore(4)`，限制同时 fork PTY 的数量为 4，防止 uvicorn 多线程下多 `run_id` 同时去新建 PTY。造成卡死
	
- **第二层，Session 池上限**：`CLUTCH_SHELL_MAX_SESSIONS` 默认 8，每个 `run_id` 最多一个 session。池满时走 LRU 驱逐——踢掉最久未活动的 IDLE/READY session，但不会动 BUSY 的。
	
- **第三层，工作区互斥锁**：`workspace_cli_lock` 是 `per-workspace` 的 `threading.Lock`，同一目录下的 CLI 调用串行化，防止两个 `claude -p` 同时写乱仓库。
	
- **第四层，会话忙碌拒绝**：`plain_chat_turn_in_progress` 检查，同一 `run_id` 的上一条消息没处理完就进本会话队列依次跑。
	
- **第五层，全局 FIFO 队列**：`plain_chat_pool_queue`，池满时不直接报错，而是排进全局队列，有 session 释放时自动 drain。
	
- **第六层，空闲清理**：后台每 60 秒 `sweep_idle()`，清理超过 30 分钟空闲或 6 小时生命周期的 session。



## marker 轮询的 CPU 开销如何？

marker 的基本原理（`echo <marker>` → 读到 marker → 截取输出）：

轮询**不是忙等**，核心是 `select.select()` 配合 200ms 超时，无数据时 CPU 基本为 0。退避是自适应的：有部分数据但没到 marker 时 sleep 100ms，完全没数据时 sleep 50ms。

#### marker 检测有三级回退

- `clutch$` 旗提示符
	
- 正则匹配独立一行 `marker` 
	
- 旗朴素计数 ≥ 2 次



## `_merge_patch` 在高频状态更新时有没有写冲突或丢失？

>  `_merge_patch` ：后端把「当前整份 `ClutchState`」和「一小片改动 `patch`」合成新的一整份状态的小函数。

`_merge_patch` 本身是安全的——它先深拷贝 再覆盖，不存在共享可变状态。正常单轮聊天、更新不特别密。但高频更新时函数并发「读改写」同一 run 时，后提交的会盖掉先提交的，可能丢字段更新确实有性能隐患。

	问题描述： 「同一会话的多次更新，旧快照盖掉别人刚写上的字段。」

但考虑到多用应用场景多用工作流，严格节点控制链路，微调的时候也不会高频状态更新，所以没有考虑到这个点，后续项目优化的话会针对这个点进行优化

- 引入版本号比对策略
	
- 给每个 `run_id` 一把锁改，这份状态时进门排队，避免两人同时改同一份稿；
```
拿到锁
  → 读 state
  → merge 一小片 patch
  → 写回内存/磁盘
立刻放锁          ← 通常几毫秒级
```

# 安全与权限

## MCP 工具调用的输入清洗怎么做？有没有注入风险？

工具调用的消毒分几层。

### 特殊字符清洗

工具名称层面，`_sanitize_tool_part()` 会把所有非 `[a-zA-Z0-9_-]` 字符替换为 `_`，确保别名符合 OpenAI 工具名格式。这防止了名称注入。

### 风险名单匹配

风险分类层面，`mcp_risk.py` 用令牌匹配做风险检测——工具名里包含 `write/delete/remove/execute/run/shell` 等关键词就标高危。安全侧误报优于漏报。

### 权限模式分级

> 权限执行层面有四种模式：
- `ask/plan/explore` 模式阻止所有写入/执行类工具；
	
- `auto_edit` 模式自动批准文件编辑（`write_file/edit_file/apply_patch`）但 shell/delete 仍需审批；
	
- `full` 模式跳过审批门控。
	
- 还有 `tool_hooks.py` 支持用户/项目级别的 JSON 钩子规则，用正则匹配工具名和路径做自定义拒绝。


## Agent 能不能写到 workspace 之外？

> 将自己的读写文件 API：默认锁在 workspace 里

不能。所有文件系统工具（`read_file`、`search_replace`、`apply_patch`、`list_dir`、`grep`）都走 `resolve_allowed_path()`，这个函数做的是 `target.resolve()` 后检查 `root not in target.parents`——标准目录穿越防御。越界直接抛 `WorkspaceError`。


## API key 在 Sidecar 和前端之间怎么传递和存储？

[[Sidecar_token环境变量]]

传输层面，**API key 从不暴露给前端 WebView**。Tauri 生成一个 UUID v4 token 通过环境变量 `CLUTCH_SIDECAR_TOKEN` 传给 Sidecar，前端通过 Tauri 命令 `invoke('clutch_sidecar_token')` 拿到这个 token，用于向 Sidecar 做 Bearer 认证。Sidecar 侧用 `secrets.compare_digest()` 做恒定时间比较。实际的 Provider API key 只存在于 Sidecar 进程内存中，LLM 调用在 Sidecar 内完成，不经过前端。

# 前端架构

## ClutchStore 的状态管理设计？为什么选这个方案？

> [!NOTE]
> 我们**没有用 Zustand/Redux 等第三方库**，而是基于 React 18 的 `useSyncExternalStore` API 实现了一个自定义的 `ClutchStateStore` 类。

[[ClutchStore 的状态管理设计]]

选择这个方案的原因是 Store 需要管理的远不止 React 状态——它同时管理 WebSocket 连接生命周期、PTY 会话状态、后台轮询定时器、乐观更新队列、重连 hydrate 等大量命令式副作用。这些用 Zustand 的不可变模型来表达反而别扭。自定义类可以把 WebSocket 连接、PTY attach/detach、状态合并逻辑全部内聚在一个对象里，外部只通过 `subscribe`/`getSnapshot` 两个接口与 React 集成。

> Store 的核心职责包括：

- WS 连接管理（connect/send/onmessage 分发）
	
- PTY 会话管理（attach/write/resize/lane 状态）
	
- 乐观更新（optimisticPlainChatSend 等）
	
- 消息智能合并（`mergeChatMessages` 做去重和字段合并）
	
- 后台轮询降级（WS 断连时 3 秒轮询 HTTP）
	
- 重连恢复（`reconnectHydrate` 保留更丰富的本地状态）。



## 画布编辑器的数据流：拖拽 → JSON → 编译，前端怎么保证编辑即时预览？

画布用 React Flow v12（`@xyflow/react`）。

> 拖的时候只是前端立刻重画图；编译发生在保存/校验/真正 Run 时。

```
拖拽 / 连线（React Flow）
    ↓ 立刻
本地 UI 状态 nodes / edges 更新     ← 你眼睛看到的「即时」
    ↓ 拖拽结束 / 连线完成
写入 workflows 里的步骤结构（含 position、nextSteps）
    ↓ 保存、切 JSON、Run 前
canvasToCompiler() → 编译器 JSON
    ↓ HTTP
validate / save；Run 时后端 WorkflowCompiler → LangGraph
```

完整的前端修改工作流到后端编译成图链路

```
canvasToCompiler → compiler JSON
       ↓
后端 WorkflowCompiler.compile()
       ↓
对每个节点：
  _wrap_handler(node)  → 内部生成函数 _run
  graph.add_node(node_id, _run) 
       ↓
再加 无条件边 / 条件边，通过 when 条件边走 add_condition_edge 则需要 _route 根据 check_result 和human_desicion 来根据节点 path_map 走向 ；非条件边直接 add_edge 执行
       ↓
graph.compile(...) → 可执行图
```


## 大量 WebSocket patch 时前端有没有做节流/合批？

有做，利用了防抖，设计思路如下：

```
收到 state_patch
  → 校验 run_id（不对则丢弃）
  → 推进 pendingPatches[]
  → clearTimeout(已有 timer)          // 取消上一轮「安静计时」
  → timer = setTimeout(flush, 16~50ms) // 重新开始安静计时

（若在窗内又来 patch → 回到上面，计时被不断推迟）

连续 N ms 内没有新 patch → 定时器到期 → flush：
  → 取出 pendingPatches 快照
  → pendingPatches = []
  → timer = null
  → merged = mergePatches(快照)
       · 标量字段：后者覆盖
       · messages：mergeChatMessages（按 id）
       · terminal_logs：按协议追加或取最新全量
       · hybrid_executions 等：浅合并 / 现有规则
  → applyPatch(merged)    // 内部更新 this.state
  → emit()                // useSyncExternalStore 订阅者重渲染
```

# 数据持久化与修复

## 重启后 Hydrate 的完整流程？哪些状态能恢复、哪些不能？

> [!NOTE]
> 完整流程见上文

> Hydrate：把已经存在的数据 灌进内存里的活对象

**能恢复的**：聊天消息、终端日志、运行状态、工作流 ID、CLI 会话 ID、Hybrid 执行记录、Token 计数、工具步骤、待办、校验报告、shell 快照。

**不能恢复的**：LangGraph WorkflowSession（`_run_sessions` 纯内存）、MemorySaver checkpoint、活跃的 bash PTY 进程、正在执行的异步任务、交互式 PTY 通道、运行时锁、shell 池实时阻塞状态。

这意味着 Sidecar 重启后，正在跑的工作流无法从断点续跑——只能重新开始或人工放行。Plain chat 的历史记录不丢，但当前轮次的结果可能丢失（取决于崩在什么阶段）。这是一个明确的权衡：用 MemorySaver 换取零外部依赖，代价是重启丢断点。
