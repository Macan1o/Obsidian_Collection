## 三次握手 / 四次挥手（核心状态与为什么要这么做）

- **三次握手（建立连接）：**
    
    - **过程：** 1. 客户端发送 SYN，进入 `SYN_SENT` 状态。
        
        2. 服务端收到，回应 SYN + ACK，进入 `SYN_RCVD` 状态。
        
        3. 客户端收到，回应 ACK，进入 `ESTABLISHED` 状态，服务端收到后也进入该状态。
        
    - **核心考点：为什么不是两次？** 为了**初始化序列号（ISN）并确认双方的收发能力**都正常。如果是两次，旧的失效连接请求如果突然传到服务端，服务端会误建立连接，造成资源浪费。
    
- **四次挥手（断开连接）：**


- **过程：**
    
    1. 客户端发送 FIN，进入 `FIN_WAIT_1`。
        
    2. 服务端回应 ACK，进入 `CLOSE_WAIT`（此时服务端还能发数据）。客户端收到后进入 `FIN_WAIT_2`。
        
    3. 服务端发完数据，发送 FIN，进入 `LAST_ACK`。
        
    4. 客户端回应 ACK，进入 `TIME_WAIT`，等待 **2MSL** 后释放；服务端收到 ACK 后直接 `CLOSED`。
    
- **核心考点：为什么需要 TIME_WAIT（2MSL）？**
    

1. 确保最后一个 ACK 能到达服务端（如果丢包可以重发）。

2. 让本次连接产生的所有网络报文都在网络中消失，防止影响下一个新连接。

## HTTP 状态码

| **状态码类型**       | **常见核心码及面试话术**                                                                                    |
| --------------- | ------------------------------------------------------------------------------------------------- |
| **1xx** (信息)    | `101 Switching Protocols`：切换协议（如 HTTP 升级为 WebSocket）。                                             |
| **2xx** (成功)    | `200 OK`：成功；`204 No Content`：成功但无内容返回；`206 Partial Content`：断点续传/分片下载。                            |
| **3xx** (重定向)   | `301`：永久重定向（SEO会转移）；`302`：临时重定向；`304 Not Modified`：命中协商缓存。                                        |
| **4xx** (客户端错误) | `400`：请求语法错误；`401`：未认证（未登录）；`403`：被拒绝（没权限）；`404`：资源不存在。                                           |
| **5xx** (服务端错误) | `500`：服务器内部错误；`502 Bad Gateway`：网关错误（如 Nginx 找不到 Node 节点）；`503`：服务器超载；`504 Gateway Timeout`：网关超时。 |

## HTTP 缓存机制（必考）

- **强缓存（不问服务器，直接读本地）：**
    
    - `Expires`（HTTP/1.0）：服务器绝对时间，受客户端本地时间篡改影响。
        
    - `Cache-Control`（HTTP/1.1，**优先级高**）：相对时间（如 `max-age=3600`）。常见值：`no-cache`（跳过强缓存，直接走协商缓存）、`no-store`（不缓存任何内容）。
    
- **协商缓存（问过服务器，由服务器决定是否用缓存）：**
    
    - `Last-Modified` / `If-Modified-Since`：基于文件的最后修改时间（秒级，不够精准）。
    
    - `ETag` / `If-None-Match`（**优先级高**）：基于文件内容生成的唯一 Hash 值（精确到内容变化）

## 跨域解决方案

> **核心原因：** 浏览器的**同源策略**（协议、域名、端口必须完全一致）。

- **CORS**（主流）：后端配置响应头（`Access-Control-Allow-Origin: *`）。注意**预检请求（Options）**：当请求是复杂请求（如 PUT/DELETE，或自定义 Header）时，浏览器会先发一个 Options 请求测探。
    
- **反向代理（Proxy）**：在 Webpack/Vite 或 Nginx 中配置代理服务器。因为**服务器之间通信不受同源策略限制**。
    
- **postMessage**：HTML5 API，常用于多窗口、`iframe` 跨域通信。

## **Websocket 专题**

> `Websocket` 和 `SSE` 都是基于服务器向客户端推送数据的技术。

**WebSocket** 是双向通信，客户端和服务器可以互相发送数据。基于TCP协议。建立连接时，只需一次HTTP握手。

- 在客户端代码 ： 先创建实例 然后调用相关的 `onopen onmessage onclose onerror`的方法完成相关的逻辑
    
- 在服务端代码 ： 先调用库，然后创建服务器，监听对应的端口，完成监听客户端发送的消息 、 监听连接关闭事件、主动向客户端推送消息等逻辑。


**SSE** 是单向通信，仅服务器向客户端推送。基于HTTP协议，基于HTTP长链接

> TCP协议跟HTTP协议的区别

（**基础**）TCP基于传输层的基础通信协议，只负责可靠、有序、无丢失地传输数据

（**应用**）HTTP是**基于TCP构建**的应用层协议，定义了规则（**请求-响应**），有具体的固定格式（请求头、请求行、请求体）「相当于多了一层封装？」

> 「应用层」XHR 和 Axios 和 Fetch 三者的区别

**三者都是HTTP协议的通信请求工具。**

**XHR**

基于回调（回调地狱）、需通过`responseText`等属性获取，兼容性较好。而

**Fetch**

基于`Promise` 可以通过`json (),text()`等方法流式解析，支持 `AbortController` 取消请求。兼容性差一点，但两者都需手动判断状态码

**Axios**

基于XHR 封装的第三方库，封装了大量功能（拦截、自动解析，自动捕获错误、支持Promise + 配置化。）

## Cookie和Token的区别

**Cookie** 是浏览器内置的 HTTP 协议存储机制，由浏览器自动管理和携带，依赖 `HttpOnly`、`SameSite` 等属性防御 XSS/CSRF 攻击，适合传统服务端渲染、单域应用；（具备严格的同源限制）

**Token** 是业务层面的身份凭证，需前端手动存储和携带，天然支持跨域和多端场景，适合前后端分离、微服务架构。实际项目中，也常把 Token 存入 `HttpOnly` Cookie，兼顾安全与灵活性。

### **JWT的运作流程**

> JWT 「token的一种具体形式」是一种JSON格式的身份凭证包含 头部 、 载荷 、 签名

- **用户登录**：前端提交账号密码，服务端验证通过后生成 JWT 返回给前端。
    
- **前端存储**：前端将 JWT 存在 `localStorage`、`sessionStorage` 或 `HttpOnly Cookie` 中。
    
- **请求携带**：后续请求时，前端手动将 JWT 放在请求头（如 `Authorization: Bearer <token>`）（如果将JWT放到 HttpOnly cookie中就不需要这步操作）
    
- **服务端校验**：服务端解析 JWT，验证签名是否有效、是否过期，直接从 Payload 获取用户信息，无需查询数据库。


### **Cookie传递的核心**

- **后端下发 Cookie**：首次请求时，服务器通过 `Set-Cookie` 响应头把 Cookie 发给浏览器。
    
- **浏览器存储 Cookie**：浏览器解析并存储 Cookie，按域名、过期时间等规则管理。
    
- **前端自动携带 Cookie**：后续向同一（或子域）域名发起请求时，浏览器自动把符合条件的 Cookie 放入 `Cookie` 请求头，传给服务器。
    
- **后端验证 Cookie**：服务器读取请求头中的 Cookie，验证用户身份或状态。

## Web常见的攻击方式

> `XSS`---> 跨站脚本攻击  `CSRF`----> 跨站请求伪造  `SQL`注入攻击

### `XSS`**攻击（获取**`cookie`**进行交互攻击 ——>** `httpOnly`**）**

> **盗取用户信息假冒合法用户交互**

为了盗取存储在客户端的**`cookie`**或者其他网站用于识别客户端身份的敏感信息。一旦获取到合法用户的信息后，攻击者甚至可以假冒合法用户与网站进行交互

**防范措施**

在用户输入的过程中，过滤掉用户输入的恶劣代码，对特殊字符进行转义然后提交给后端 设置HTTP头 来规定浏览器可以加载的资源来源

`HttpOnly`：禁止前端通过 `document.cookie` 读取，防止 XSS 攻击窃取 Cookie

### `CSRF`**攻击（第三方网站跨域请求攻击 ——>** `SameSite`**）**

> **第三方网站跨站冒充用户定义自己操作**

诱导受害者进入第三方网站，在第三方网站中，向被攻击网站发送跨站请求 第三方网站冒充用户定义自己操作

### **防范措施**

阻止不明外域的访问 和 提交时要求必须本域才能获取的信息

`SameSite`：防止 CSRF 攻击，值为 `Strict`/`Lax`/`None`
