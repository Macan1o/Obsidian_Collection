## 一、如何快速学习新技术 ⭐

> 我的学习方法核心就一句话：**不做从零开始的阅读者，做带着问题的验证者。**

**1. 先找锚点，从已知映射未知。** 新技术如果和已有知识有重叠，从重叠处切入会快很多。比如从TS的语法特性映射到 Python 语法特性，就让我更快地掌握这门语言的边界，就不是从零开始；从前端框架的响应式思维去理解别的框架，也是同一个道理。

**2. 全新领域就先跑通最小 demo。** 把主链路走一遍，产生「<mark style="background:#d3f8b6">问题意识</mark>」之后再回头啃文档——比从头通读文档效率高得多。因为这时候读文档是**查证式阅读**，不是扫盲式阅读。

**3. 问题驱动的学习才留得下来。** 我的每次技术栈扩展基本都有明确的项目触发，是项目跑到那里我跟过去的，不是为了丰富履历。这样学到的是<mark style="background:#d3f8b6">知道这个技术解决什么问题、什么场景下不该用它</mark>。

**4. 源码学习分三个阶段：**
- **骨架认知**：先建立模块间的全局心智模型，把握端到端怎么走；
	
- **逐模块深挖**：对每个模块问四件事——问题是什么、怎么解决、为什么这么选、边界在哪；
	
- **细节查证**：对关键逻辑单独拎出来确认，确保理解闭环。

**5. 把踩过的坑沉淀下来。** 比如桌面打包时运行时环境差异的那几个问题，每个都是踩坑之后才真正理解，这些认知很难从文档直接获得。坑记下来，第二次遇到就是「<mark style="background:#d3f8b6">识别题</mark>」而不是「<mark style="background:#d3f8b6">解答题</mark>」。

## 二、开发时注意哪些难点 ⭐

> 我把开发难点分成两层：宏观层面和微观层面

### 微观层面：我最关注两件事

**1. 状态一致性。** 一致性问题往往藏在异步链路里——数据什么时候到、到了以后以哪份为准、多个消费方看到的版本是否一致。稍有疏漏，表象就是白屏、数据错乱、界面和真实运行状态对不上。我在项目里坚持一个原则：**全系统只能有一份`真相`，其他都是基于它的投影**。

**2. 边界条件。** 正常的 demo 场景测不出问题，生产环境很快暴露：极端数据量、并发竞态、进程中断、用户非常规操作。所以我在设计阶段就会问自己"这个东西坏的时候是什么样"，把失败路径当成正常路径来设计，而不是事后补丁。

### 宏观层面：多维度的难

做一个项目的难不是单点的某个 Bug，而是**同时要考虑多个互相牵制的维度**。拿本地多 Agent 编排控制台来说：如何将几条异构执行链捏成同一套可监督的状态闭环？怎么保证多引擎统一调度下的一致性？

我的方法是**分而治之**：先把问题域拆开，每个子问题独立设计、独立验证，最后再组装。比如通过设定唯一真相 State ，通过主键串联，以及分流机制完美实现多引擎调度一致性

## 三、核心技术难点（宏观视角）⭐

> 最大的难点不是 API 怎么用，而是如何把几条异构执行链捏成同一套可监督的状态闭环

用户侧是零代码画布和 Chat；后端同时存在 LangGraph 工作流、MCP ReAct 工具循环、Hybrid 长驻 bash/PTY，以及图级人工闸门与工具级审批等不同控制流。每条链的产物形态不同（聊天气泡、终端输出、文件变更、工具步骤、等待人工…），但前端必须只投影同一份运行态契约（`ClutchState`），通过 WebSocket 增量更新，而不能在 React 里另搞一套编排真相。所以难在<mark style="background:#d3f8b6">「多引擎统一调度下的一致性」</mark>，如何保证它们共享同一条 run 生命周期时仍然逻辑自洽、失败可操作。可以拆成四层：


<mark style="background:#d3f8b6">1. 契约与投影 </mark> 
各链副作用（消息、终端、改文件、工具步骤、池状态、等待人工）必须收敛进唯一可投影状态，经 `state_patch` 推给前端，禁止第二套真相 [[「前端」ClutchStore 的状态管理设计]]

<mark style="background:#d3f8b6">2. Hybrid 长驻与边界  </mark>
- 多轮上下文不能每次冷启 subprocess，所以要长驻 PTY；但 PTY 没有自然的 turn 结束，要用 marker 轮询切边界，再配合 CLI `--resume` 延续会话。
	
- 池化后还有同工作区并发互锁，因此需要 workspace 锁与 LRU；池满则全局排队，而不是丢消息。

<mark style="background:#d3f8b6">3. 策略路由与解包处理  </mark>  [[策略路由与解包处理]]
用 ProviderSpec / 运行策略把 MCP、PTY、云 LLM 收成少数出口；返回值强制解包，避免契约漂移直接打进 Chat。

<mark style="background:#d3f8b6">4. 双层 HITL 与恢复 </mark> 
- 图级 interrupt/checkpoint 与工具级风险闸门并存：状态必须和 WebSocket 投影对齐，决策用完即清。[[图级和工具级HITL以及Check节点]]
	
- checkpoint / 落盘与重读策略，保证暂停续跑、进程恢复后监督面仍一致。

## 四、解决问题的能力

遇到问题我的第一反应是**往下挖根因，而不是在症状层打补丁**。

典型例子：富文本编辑器处理复合数据对象时会触发底层引擎的数据错乱。我没有绕着改上层逻辑，而是直接去读底层引擎的源码，定位到是内部数据模型的指针层面问题，最终用序列化中转的方式彻底绕开了污染路径——全程字符串交接，从机制上杜绝复发。

另一个例子是：工作流在人工审批之后恢复重跑，刚恢复执行，马上又回到挂起状态，看起来像路由逻辑出了问题。如果停在症状层，顺手就会在路由上打补丁，比如放宽条件、加重试次数。但真正的根因是：**上一轮的检查结果（失败信号）还残留在状态里**，恢复之后立刻又被同一个失败条件短路了回去。修法不是绕过它，而是在恢复时把用完的决策数据清掉，让每一次重跑都从干净的状态出发。

因此我的方法论是：**找到最小复现路径 → 在最接近根因的地方修 → 验证不复发**。症状层打补丁的问题在于，同样的 Bug 会换一个地方再出现一次。

## 五、做项目的整体思路

> 做工程化项目越久越觉得：**核心不是某个库怎么用，而是在正确的时机处理状态、把兜底做扎实。**

我的流程是固定五步：

1. **先看输入输出**——输入是什么（用户配置、需求描述），输出是什么（一个可交付的产品），中间的转换就是项目本体；
	
2. **再选载体**——为每个核心环节做技术调研，选择合适的承载方式，逐个确定；
	
3. **构建主链路**——围绕核心链路搭工具函数，先把 0→1 跑通，中间穿插兜底机制保证健壮性；
	
4. **提高质量**——跑通之后再解决更精细的问题：多角色输出的交接逻辑、权限控制、逻辑分流，慢慢丰富完善；
	
5. **持续迭代**——上线不是终点，根据实际使用反馈做功能迭代。

这套思路的底层逻辑是：**先保证跑通，再保证可控，最后才谈优化。** 顺序不能反。

## 六、协作与分歧处理

意见不一致时，我先区分**分歧在哪个层面**：

- **目标层面不一致**：这不是讨论能解决的，需要拉齐优先级，必要时引入更多人参与判断；
- **方案层面不一致**：把两个方案的约束和权衡摆出来，用数据或小范围验证说话，而不是靠说服。


---

## 七、复盘：如果优化，会改什么

复盘时我关注的是**结构性短板**而不是修修补补：

1. **上下文传递策略**——节点多起来之后全量拼接会丢细节，要引入压缩策略；
2. **并行场景的可观测性**——单节点可以并行，但并行状态没有充分展示给用户，监督面要跟上能力面；
3. **策略配置化**——风险控制目前偏内置，误报漏报都要改代码，应该开放给用户自主配置。

复盘的原则：**能落地的复盘才叫复盘。** 每一条都要指向明确的改进动作和判断依据，而不是"下次注意"。

## 九、自我评价：三个词

**根因思维**——遇到问题不停在症状层绕。拖拽回弹、数据指针冲突、异步闭包陷阱，都是先搞清楚底层机制才找到干净解法，否则打补丁迟早复发。

**问题驱动**——技术栈每一次扩展都有具体场景触发。状态持久化、断点恢复、条件路由完美对应 LangGraph的 checkpointer、interrupt、conditional edges ，果断选择新框架；从 Web 到桌面端，问题在哪我跟到哪

**执行闭环**——想到了就做，做了就落地到可用。有次半夜想到解决焦点死锁的思路，当晚调试通过，第二天集成进去。**想法到实现之间的距离，我不让它隔夜。**
