### Q2「为什么选 LangGraph？自己写状态机不行吗？ 用 Dify / Coze 不行吗？」

自写状态机需要解决三件事情：状态持久化、断点恢复、条件路由。

1. LangGraph 的 `checkpointer + interrupt + conditional edges` 天然就是干这个的，自研等于重造且容易出边界 bug。我聚焦的点在**编译层**（JSON→图的校验与转换）和**执行层**（引擎路由、PTY、审批门控）
	
2. **Dify/Coze 是托管云平台**，我们的流水线要调本地 CLI。云平台做不到也没法定制审批闸门。




### Q3 ClutchStore 的状态管理设计？为什么选这个方案？

> [!NOTE]
> 我们**没有用 Zustand/Redux 等第三方库**，而是基于 React 18 的 `useSyncExternalStore` API 实现了一个自定义的 `ClutchStateStore` 类。

[[「前端」ClutchStore 的状态管理设计]]

选择这个方案的原因是 Store 需要管理的远不止 React 状态——它同时管理 WebSocket 连接生命周期、PTY 会话状态、后台轮询定时器、乐观更新队列、重连 hydrate 等大量命令式副作用。这些用 Zustand 的不可变模型来表达反而别扭。自定义类可以把 WebSocket 连接、PTY attach/detach、状态合并逻辑全部<mark style="background:#d3f8b6">内聚在一个对象</mark>里，外部只通过 `subscribe`/`getSnapshot` 两个接口与 React 集成。

> Store 的核心职责包括：

- WS 连接管理（connect/send/onmessage 分发）
	
- PTY 会话管理（attach/write/resize/lane 状态）
	
- 乐观更新（optimisticPlainChatSend 等）
	
- 消息智能合并（`mergeChatMessages` 做去重和字段合并）
	
- 后台轮询降级（WS 断连时 3 秒轮询 HTTP）
	
- 重连恢复（`reconnectHydrate` 保留更丰富的本地状态）。

#### 大量 WebSocket patch 时前端有没有做防抖/合批？

有做，利用了防抖，设计思路如下：

```
收到 state_patch
  → 校验 run_id（不对则丢弃）
  → 推进 pendingPatches[]
  → clearTimeout(已有 timer)          // 取消上一轮「安静计时」
  → timer = setTimeout(flush, 16~50ms) // 重新开始安静计时

（若在窗内又来 patch → 回到上面，计时被不断推迟）

连续 N ms 内没有新 patch → 定时器到期 → flush：
  → 取出 pendingPatches 快照
  → pendingPatches = []
  → timer = null
  → merged = mergePatches(快照)
       · 标量字段：后者覆盖
       · messages：mergeChatMessages（按 id）
       · terminal_logs：按协议追加或取最新全量
       · hybrid_executions 等：浅合并 / 现有规则
  → applyPatch(merged)    // 内部更新 this.state
  → emit()                // useSyncExternalStore 订阅者重渲染
```




### Q4 简单说一下LangGraph 运转原理

[[LangGraph运转链路]]

> 主要分为「编译期」和「运行期」两个时期说明：

#### 编译期

**节点的编译**

通过闭包函数将前端 type 映射到对应节点的执行逻辑，因为 LangGraph 的回调仅支持 state 到 state 的单参逻辑，因此需要利用闭包捕获链路固定的 node、workflow 等信息 ，`_run` 闭包函数只接受节点的动态变化状态。相当于一层透传，然后特殊的 human_gate 节点也就是需要人工审核的节点需要进行注册到 LangGraph 中便于利用 interupt_brfore 执行暂停逻辑。

**边的编译主要分为「条件边编译」和「非条件边编译」**

条件边也就是上游是 check 和 huaman_gate 的节点，需要注册到 LangGraph 的条件边数组中，非条件边注册到非条件数组中，然后将不同选择对应节点的分支节点注册成 path_map 进行映射。

#### 执行期

条件边需要利用闭包函数 `_route` 读取编译后的 path_map 来更改 LangGraph 的 `snapshot.next` 从而指导 LangGraph 运行。非条件边只需要按节点往下执行即可。

最终收束成 LangGraph 调 `_run` → 根据状态看边 / 问 `_route` → 去下一 id 的运转链路




### Q5「HITL + MCP ReAct 循环的风险分级怎么做的？」

[[图级和工具级HITL以及Check节点]]

<mark style="background:#d3f8b6">图级</mark>

工作流执行到 human_gate 节点时，运行状态把状态写成 awaiting_human ，LangGraph 在这里挂起，注明 pending 类型，节点暂停，前端弹出审批，用户操作后，Sidecar 带着拿着这次选择 resume ；条件边的 `_route` 根据结果查 path_map ，再跳到对应下一节点，图继续流转

<mark style="background:#d3f8b6">工具级</mark>

ReAct模型里先给出 tool_shell ，Sidecar 检查是否高危（写/删/Shell），若命中且开启了风险暂停，这次工具不执行，将当前上下文存到 `mcp_pending` 中，注明 pending 类型，推 `human_required` 事件给前端弹审批卡片；低危和内置白名单工具（只读、todo 之类）直接执行。

审批去重用工具名+参数的 SHA-256 前 16 位做 key——同一批操作已批过的不再反复弹窗。循环本身有 24 步上限，防死循环烧 token。

MCP服务：传输层 stdio 跑本地 Server 或者 Streamable HTTP（JSON-RPC 2.0）连远程。

人点击 Allow 后落盘，然后进行下一轮ReAct，并且执行`pop_pending`，approve 还会记 approval key，防止下一相同调用自动再拦或重复打扰。

<mark style="background:#d3f8b6">check节点</mark>

根据 handler 内部逻辑「LLM」判断 passed / failed 然后继续走条件边的逻辑

### Q7「Workflow 编译器讲细一点」

> 主要分为三部分：<mark style="background:#d3f8b6">校验</mark>、<mark style="background:#d3f8b6">节点编译</mark>、<mark style="background:#d3f8b6">边编译</mark>

#### 1. 校验

- 先进行结构校验以及图级检查——必须有 end 节点、start 必须连通、BFS 检测孤立节点；
	
- 出编译执行校验，一个节点的出边要么全带条件「when: passed/failed、approve/reject/retry」要么全不带，混着走会导致路由歧义，直接拒绝编译；

#### 2. **节点编译**

将五类节点注册成闭包包装的 handler ——LangGraph 的节点回调签名只有一个 state 参数，因此需要通过闭包函数捕获 node/workflow 上下文「节点自己的配置（agent、instruction、校验规则）」并且执行对应 handler ，最终返回这个只吃 State 的闭包函数。 [[LangGraph闭包函数逻辑]]

#### 3. **边编译**

根据 when 字段将边分为条件边跟非条件边，条件边通过闭包函数读取编译后的映射关系来指导 LangGraph 运行；非条件变就按顺序运行




### Q8「人工审批节点怎么实现的？」

[[LangGraph运转链路]] | [[WS 事件专题]]

> 基于 LangGraph 原生机制 + 一些工程处理

- 编译时将所有人工审批的节点收集起来，注册到 `interrupt_before` 事件，让图在到这些节点的时候自动挂起
	
- 每次运行时，checkpointer 把状态快照存下来，进程不丢状态；
	
- 当到决策节点时，状态改为 `huamn_decision` 的状态，然后通过 `update_state` 的 WS 事件更新决策字段，通过 `Command(resume)` 恢复执行

> [!NOTE] 关键坑
> retry 恢复时必须清空上一轮的检查结果（check_result），否则旧的失败信号还在状态里，resume 之后马上又被同一个失败条件短路回去，图走不动。这是我实际踩过修掉的。




### Q9  State 全局管理是怎么做的

> 状态的主键是 `run_id` —— 每个会话 / 每次运行一份 `ClutchState`。所谓「全局」，指的是这一次 run 的唯一真相

跨会话并行时，多个 run_id 各跑各的，根据不同的 run_id 存储：内存 `_run_states[run_id]`，磁盘 `states/{run_id}.json`，WebSocket 按 run_id 订阅；前端 `clutchStore` 收到 patch 时 run_id 对不上直接丢掉。

真正容易撞车的是共享本机资源，用锁和队列挡（同一 workspace 互斥、session 池限制、全局排队池）。状态更新统一 `_merge_patch` → `_commit_run_state`（写内存+落盘）→ `state_patch` 推前端，React 只负责投影。

#### 三锁维护状态统一

> [!NOTE] 三者区别
> 按照他们的介质不同，池内锁就「锁 session 字典」，然后拿到锁才开始改状态，然后释放；路径锁就是「锁工作区路径」拿到锁才允许 CLI 进行处理； file_lock 就是「锁文件」，只有拿到锁才能改文件里的数据


[[三锁维护状态统一]]

```
发消息
  │
  ├─ 需要 Hybrid shell？──是──► get_or_create 【池内锁】
  │                              │
  │                              ▼
  │                         跑 CLI 【路径锁】
  │                              │
  │                              ▼
  │                         mark_idle 【池内锁】
  │
  └─ Agent 改文件 / 回滚 / 写 history？
         └─ 是 → open + 【file_lock】→ 读改写 → 解锁
```




### Q10「进程挂了 / 重启了，运行还能续上吗？」

#### 运行态落盘与重启恢复

基本逻辑是，每当状态发生变更就走 `_commit_run_state` 逻辑，先写在内存字典，然后根据唯一主键 `run_id` 通过 `save_run_state` 同步全量覆写 JSON 到磁盘上。此时进程挂了有两种情况：

- 内存没数据：WS 连接时调 `sync_run_state_from_disk()` 发现内存没有数据，然后调磁盘，文件不存在 → 全新 initial_state，JSON 损坏也当全新处理。
	
- 内存有数据：根据新旧判断规则来保留唯一可信源，针对两种情况：若状态一致则看消息条数，若状态不一致，则优先使用 done 状态的可信源，因为挂起后的 running 状态为僵尸状态

> [!NOTE] 注意
> LangGraph 的 MemorySaver checkpoint 不落盘，因此回不到断点只能恢复对话历史

#### 为什么用 MemorySaver 不用 SqliteSaver？

MemorySaver 是内存 checkpointer，适合单进程本地应用 —— 桌面工具一个 Sidecar 进程，没有多进程共享状态的需求，持久化我已经用运行态落盘 + 恢复机制覆盖了。因为我是自己做得提效应用，不需要进程/服务重启不丢 checkpoint这种企业级部署，因此就没有考虑




### Q11「为什么 Tauri 不用 Electron？为什么后端是独立 Python 进程？」

<mark style="background:#d3f8b6">Tauri</mark>：用打包 Chromium，用系统 WebView，包的体积更小。并且 Rust 侧管进程很可靠。我的进程 Token 就是由 Rust 注入到前端完成进程级鉴权的

<mark style="background:#d3f8b6">Python Sidecar</mark>：前端 TS 进程做不了进程管理和长驻 PTY。

所以架构是 Tauri 负责壳，spawn 一个 PyInstaller 打包的 FastAPI sidecar，前后端只走 loopback HTTP/WebSocket，启动时注入会话 token 做鉴权（恒时比较），前端禁止直接碰文件系统和子进程——权限边界干净。




### Q12「策略式引擎路由是什么？为什么要三条路径？」

> [!NOTE] 原理
> 策略式引擎路由解决的是异构 Agent 执行后端的复杂配置维护问题，将所有 Agent 收束为 **CLI 与内置 Agent 两种执行形态**

> 对不同类型的 Agent 做不同的逻辑处理  [[执行引擎分流]]

- CLI ：配置字典统一维护每个工具的二进制名、旗标、会话续接模式等差异。兜底分两层：引擎内部经二进制可用性检测后，优先走持久 PTY hybrid 会话（支持会话续接与 snapshot 接力），遇到多行 payload 或危险命令时降级为一次性子进程
	
- 引擎本身不可用（未安装/未连接）时直接降级到内置云端的 LLM Router

#### 可用性探测逻辑实现

`/api/tools/status` 驱动前端下拉：没装的 CLI 不出现或标未连接；路由时若强行指定不可用引擎，应清晰报错（「No API key / binary missing」），而不是静默落到错误路径。

模型测连是 `POST /api/models/test`，CLI 工具状态和 Connect 是 `/api/tools/status`、`/api/tools/connect`，MCP Hub 探测也在 settings 路由里。

这些都在本机 Sidecar 里查 PATH、打 Provider API、起 MCP 子进程。Tauri 主要负责拉起 Sidecar、注入 token、窗口和系统能力；没有它桌面端起不来本地后端，但「连没连上」的判定逻辑不在 Rust 侧。

	相关逻辑实现都在对应的手脚组件里面




### Q13 为什么要做 PTY 会话池，而不是每次 `subprocess` 起一次 CLI？

[[CLI 的 Hybrid 完整链路实现]]

每次 `subprocess` 起 CLI 启动开销大，而且进程一结束环境、工作目录和会话上下文就丢了，多轮对话很难真正续上。

PTY 会话池按 `run_id` 保活一条 bash，在同一终端里反复跑 CLI，既能复用进程和环境，也方便带 `--resume` 做长会话；同时用池限制并发、空闲回收，并在 Hybrid 失败或不适合时回退 `subprocess` ，兼顾连续性和稳定性。

#### 池化复用 / LRU / 工作区互斥——各自防什么？

[[池化复用、LRU、工作区互斥]]

- 池化： 多 Chat session 共享有限 shell 槽位（`CLUTCH_SHELL_MAX_SESSIONS`）
	
- LRU 驱逐： 槽满时踢最久未用，防 shell 开太多占满内存/句柄；池满时优先腾空闲位
	
- 工作区互斥锁： 同目录并发 `claude -p` 会互锁/写乱仓库，所以同 workspace 串行  

池满时新 session 进全局 FIFO（`queued_pool`），而不是直接拒绝——体验上「排队」优于「报错」。

#### 会话快照 + --resume 怎么配合？

`--resume` 管 CLI 侧逻辑会话：首轮生成并保存 `cli_session_id` 「多轮会话id」，下一轮拼命令时带上 `--resume <id>` 让 Claude 等 Agent 自己接着聊。

会话快照管 Clutch 侧磁盘落入：每轮 Hybrid 成功后把 `run_id`、工作区、`cli_session_id`、任务摘要写到 `shell_snapshots/{run_id}.json`。

Bash PTY 活跃时靠 `--resume` 续聊；shell 断了重建时靠 `load_snapshot` + `format_handoff_prefix` 把快照垫进 prompt。

#### PTY 的输出边界怎么判定？为什么不用 EOF？

长驻会话里 EOF 只在会话结束时出现，单条命令结束没有信号——所以发命令时**尾部注入一个唯一 sentinel marker**（echo 一个带 uuid 的标记），持续轮询输出流直到 marker 出现，中间的就是这条命令的输出。解析前还要做 ANSI 转义剥离，否则颜色码会污染内容匹配。然后再数据清洗回传渲染




### Q14「PIL 颜色量化那条——设计规范提取怎么做的？」

> [!NOTE] 设计理念
> prompt 形容颜色不稳定。所以用 PIL 颜色量化 从参考图抽调色板，用 Playwright 爬真实站点 CSS 抽字体/间距/色板，再经校验网，把可执行的设计规范交接给编码 Agent——统一视觉 SSOT。

**PIL 颜色量化**

缩图到 150×150（控制计算量），MEDIANCUT 量化成 12 个代表色，统计像素占比，HSV 分类成 primary/secondary/accent/neutral 四桶，得到精确 hex 调色板；

**OCR**

pytesseract 提取可见 UI 文字（灰度化提升准确率），给了组件线索；

> 这上述拼成结构化 prompt 片段注入，并**强制约束模型必须用这些 hex**，禁止自己编颜色。

#### 三重安全网

[[两层Design HTML防护机制]]

1. 提取层：图/站点物理采样，不靠模型瞎编 hex
	
2. 校验层：token 完整性、对比度/必填字段、与预设 brand spec 对齐
	
3. 交接层：确认后的 design spec 再进生成/编码 Agent；人确认过的才算真相  


> 对应产品上有「确认 design spec → 再出高保真」的闸，而不是一次生成到底。

### Q1「编辑器焦点捕获的动态补行算法那一部分，讲讲问题和解法」

富文本编辑器（类 Notion）里，点击文档底部空白区域时，原生行为会出现焦点死锁，光标无法在我想要的位置插入。笔记书写的体验感不是很好。

因此我**基于 DOM 空间坐标映射**——算出点击的 Y 坐标折合多少行高度（Y 轴点击深度）程序化补空行并**清除继承格式**，再重定向光标到新行末尾。绕开原生焦点机制。




### Q2「你简历里 Tiptap 和 Quill 都出现了，为什么用两个编辑器？」

这其实源自于一次技术栈的更新。Quill（Delta 模型）是早期富文本模块。后来做复杂定制「插入评论功能」时碰到 Delta 模型的限制——自定义 Blot 继承扩展复杂，DOM 和数据模型双向转换时出现**指针/游标冲突**。解法是序列化中转 + DOM 属性过渡。最终结合从原生到 React 框架的升级，我选择了更加适配 React 的 Tiptap 编辑器。让我今后更加重视前期技术选型以及技术栈边界的思考



### Q3「双向链接怎么设计的？」

每个文档解析 `[[标题]]` 语法生成引用边，存 source→target 关系表；反向引用就是 target 维度的索引查询；"差量同步"指编辑时只重算受影响文档的引用关系而不是全库重建。可视化层用 D3 力导向图渲染文档关系网络。



### Q4「RAG 那块：HNSW 是什么？为什么不用 IVFFlat ？怎么和 BM25 混合？」

> [!NOTE] 概念记忆
> HNSW 是分层小世界图索引：向量入图，查询从顶层快速跳到底层近邻，高召回低延迟，**不需要训练、数据量小也能用**；IVFFlat 要先聚类建倒排，数据量小时质心不准，还依赖 periodic rebuild。个人知识库规模下 HNSW 是标准答案；

<mark style="background:#d3f8b6">混合检索</mark>：向量语义相似 + BM25 关键词精确匹配，用 **RRF（倒数排名融合）** 合并两路结果——语义找"意思相近"，BM25 找"精确命中术语"（比如函数名、错误码），互补。最终生成全新排名，这对于一个三四百篇的技术数据库已经足够了



### Q5「技术栈里为什么 Convex 和 PostgreSQL 并存？」

- Convex 是实时协作层（实时同步、订阅式更新，省掉自己写 WS 广播和冲突解决）目前只做了一个简单的聊天模块，后续可能尝试做一下文档多人编辑功能
	
- PostgreSQL 是持久层 + 向量检索（pgvector）

两者在实时性和查询能力分别取最优，不是冗余。
