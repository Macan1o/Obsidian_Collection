# 本地多 Agent 编排控制台
## 平常是怎么学习的

> 我有两个层面的学习，分为理论学习和实战源码学习。

关于理论学习我的习惯是先找锚点。新技术如果和已有知识有重叠，从重叠处切入会快很多。比如从JS的角度映射到Python的学习中。如果是全新领域，我会先跑通一个最小 demo 把主链路走一遍，有了问题意识再去啃文档，比从头读文档效率高得多。

> 关于实战源码学习，我分为了三个阶段。

- 第一个阶段是先建立骨架认知，先建立各个模块间的全局心智模型。对全局的边界有一个把握「<mark style="background:#d3f8b6">端到端怎么走</mark>」
	
- 第二个阶段是逐模块深挖吃透各个模块的技术细节「<mark style="background:#d3f8b6">问题是什么，怎么解决，为什么这么选，边界在哪</mark>」
	
- 第三个阶段就是细节查证，通过双链连接对比较重要的逻辑单独拎出来说明。「<mark style="background:#d3f8b6">比如LangGraph的单参回调特性解决方案</mark>」



## 简单说说做项目的思路

随着做工程化的项目并且积累经验后，我越来越觉得核心不是某个库怎么用，而是在正确的生命周期、正确的时机处理状态，并把兜底做扎实。

比如我的 clutch 项目。先看输入输出，输入的是用户在各个节点配置好的提示词。输出的是一个从0到1的产品。

然后开始思考我要借助什么载体实现这一过程 ？因此就先技术调研，发现 LangGraph 比较适合。以此类推选择好各个功能适合的载体，监督用 WebSocket 投影 ClutchState，本地执行用 CLI / Hybrid PTY。然后就是根据这一核心链路构建工具函数帮助我们实现产品的构建。中间穿插着各种兜底处理机制保证工程项目的健壮性。从而实现完整链路的跑通。

跑通后就要对质量进行提高，比如多 Agent 输出与交接？权限逻辑如何实现？多种 Agent 的逻辑分流？然后慢慢丰富完善这个项目。再进行功能迭代更新。

在这一个过程中出现bug是很正常的，系统化排查解决bug能力也是提高自己工程能力关键的一环

## 一、产品定位与动机

### 为什么要做这样一个产品？

是这样的，我在公司负责应用从零到一落地：产品给名称，我这边要交付。因为有一些限制因素，所以一开始选择跟 AI 一步步聊，质量不稳定；后来选择出高效的提示词把流程沉淀成 Skill，并不断优化，形成多链路节点监督机制

```
规则与红线确认机制
功能选型
出设计稿
形成视觉资产
按稿还原
粘性打磨「间距呼吸感、或者一些简单动效」
```


经过这套流程过后我发现最后质量相对来说比较容易把控。输出结构比较统一。并且后续如果增加节点的话也方便配置。也便于后期维护。

后来就是既然节点链路的话我觉得可以打造一个多Agent工作流，刚开始是打算用n8n的，后来发现n8n它能跑节点，但执行黑盒，人工随时叫停也不顺手。于是我就打造了一个基于LangGraph的多 Agent 编排与监督控制台。状态可看、审批可拦、输出可控。便于不断优化调整，并且减少开发难度，可以根据多样化的节点配置完成需求的多样化


## 二、技术选型与竞品对比

### 为什么选用 LangGraph

我们之所以选择LangGraph是工作流运行时需要一个可靠的状态机。多 Agent SOP 不是线性脚本：有分支、有自动检查、有人工门控。尤其是人审节点，图必须能 interrupt 挂起、等人决策后再 resume——这正好是 LangGraph 的强项；再加上 checkpoint，本地长跑可恢复。因此决定选用现有成熟的LangGraph框架

### 为什么不选择更加成熟的n8n？

如果只是单纯执行脚本把表单、数据库、通知串起来，我会用n8n，没必要自研。n8n虽然也能跑节点，但执行黑盒，人工审核叫停挂起功能也不是很流畅。结合业务我需要每个节点输出人为审核 HITL 精确挂起续跑，避免各节点输出黑盒并且在本地工作区里写代码、改文件、跑 CLI、互相交接。因此决定自己基于LangGraph封装多 Agent 编排与监督应用

```
n8n 自动化的是系统之间的数据；我们自动化并监督的是 Agent 的业务处理。
```


### 有没有了解过 LangSmith / LangFuse ？

> 上面两者是观测层，主要是给 LLM 应用做追踪、评测、成本分析的可观测平台。而我的项目是实际应用层

并且功能逻辑不同，LangSmith、LangFuse 主要给链路打 trace、看 span、比 prompt、做评测，多数挂在应用外面，帮研发「看见模型怎么跑」，不负责一些像零代码拖 SOP，调度人审闸门的功能逻辑。结合其观测层的属性，若以后要做更细的 prompt/token 分析，可以把 Clutch 的 run 接到它们进行分析


### 和 Dify/Coze 有什么区别？

Dify、Coze 更偏 云端/可托管的 LLM 应用搭建台，无法深度碰文件系统、子进程、长驻 bash PTY，也无法调度成熟的 Claude Code、Codex 这类本地 CLI

## 三、端到端链路

### 一次用户发送消息，端到端怎么走？

Tauri WebView → HTTP/WS → FastAPI →

- if `plain chat`： EngineRouter 选路 → MCP ReAct 或 PTY 或者 云 LLM → 状态 patch 经 WebSocket 推 `ClutchState` → React 三栏投影（Chat / Terminal / Changes）。
	
- if `workflow`：JSON → WorkflowCompiler → LangGraph invoke → 节点内再调同一套 EngineRouter

## 四、核心技术难点

### 最大的技术难点是什么

> 最大的难点不是 API 怎么用，而是如何把几条异构执行链捏成同一套可监督的状态闭环

用户侧是零代码画布和 Chat；后端同时存在 LangGraph 工作流、MCP ReAct 工具循环、Hybrid 长驻 bash/PTY，以及图级人工闸门与工具级审批等不同控制流。每条链的产物形态不同（聊天气泡、终端输出、文件变更、工具步骤、等待人工…），但前端必须只投影同一份运行态契约（`ClutchState`），通过 WebSocket 增量更新，而不能在 React 里另搞一套编排真相。所以难在<mark style="background:#d3f8b6">「多引擎统一调度下的一致性」</mark>，如何保证它们共享同一条 run 生命周期时仍然逻辑自洽、失败可操作。可以拆成四层：


<mark style="background:#d3f8b6">1. 契约与投影 </mark> 
各链副作用（消息、终端、改文件、工具步骤、池状态、等待人工）必须收敛进唯一可投影状态，经 `state_patch` 推给前端，禁止第二套真相 [[「前端」ClutchStore 的状态管理设计]]

<mark style="background:#d3f8b6">2. Hybrid 长驻与边界  </mark>
- 多轮上下文不能每次冷启 subprocess，所以要长驻 PTY；但 PTY 没有自然的 turn 结束，要用 marker 轮询切边界，再配合 CLI `--resume` 延续会话。
	
- 池化后还有同工作区并发互锁，因此需要 workspace 锁与 LRU；池满则全局排队，而不是丢消息。

<mark style="background:#d3f8b6">3. 策略路由与解包处理  </mark>  [[策略路由与解包处理]]
用 ProviderSpec / 运行策略把 MCP、PTY、云 LLM 收成少数出口；返回值强制解包，避免契约漂移直接打进 Chat。

<mark style="background:#d3f8b6">4. 双层 HITL 与恢复 </mark> 
- 图级 interrupt/checkpoint 与工具级风险闸门并存：状态必须和 WebSocket 投影对齐，决策用完即清。[[图级和工具级HITL以及Check节点]]
	
- checkpoint / 落盘与重读策略，保证暂停续跑、进程恢复后监督面仍一致。

## 六、复盘与改进

### 如果需要对项目进行优化，你会改什么

- 多Agent节点的输出内容拼接策略 compact 处理「目前上下节点的输出还是通过全量拼接的方式进行的，如果十几个节点的时候可能会出现细节丢失情况，后续需要对其压缩」；
	
- 编译器对并行 fan-out 的可观测性加强「目前单节点是可以并行多节点，但是状态没有对多节点进行显示，这个后期也是需要对齐优化的」；
	
- 风险表可配置化「MCP 风险仍主要靠内置 token 表，误报/漏报都靠改代码。我会把风险策略做成可配置，后续由用户对风险操作进行自主配置」

## 七、产品与协作

### 一个典型的 0→1 落地，从配置到交付大概多久？

一个典型的 0→1 流程是：规则确认 → 功能选型 → 出设计稿 → 视觉资产 → 按稿还原 → 粘性打磨。每个节点对应一个 agent_task，中间有 check 自动校验和 human_gate 人工审批。

配置工作流大概 10 分钟，跑完一条链路交付产品大概 40-60 分钟取决于 LLM 响应速度和人工审批环节，最终交付质量比纯 prompt 对话提升明显——主要体现在输出结构统一、视觉一致性可控、失败可回溯。

# 全栈实时智能效率工作站

## **核心能力一：解决问题**

遇到问题我的第一反应是往下挖根因，而不是找现成方案套用。举个典型例子：开发 CloudNote 时，Quill 编辑器在处理含有评论内容和时间戳的复合对象时会触发内部深拷贝 Bug，导致数据错乱。我直接翻了底层 Parchment 引擎的源码，定位到问题出在内存指针层面，最终用 JSON 序列化 + HTML `data-*` 属性中转的方式，以全程字符串交接彻底绕开了指针污染路径。

同期还解决了焦点死锁的问题——光标会卡死在代码块边缘无法逃逸。我通过读取 `e.clientY` 和 `getBoundingClientRect().bottom` 做坐标深度映射，算出需要动态补几行空行并清洗格式，实现了类 Notion 的自由点击体验。

这两个问题表象是 Bug，根因在底层机制的边界没有被正确处理。我认为解决问题能力的核心是：找到最小复现路径，在最接近根因的地方修，而不是在症状层打补丁。

---

## **核心能力二：学习能力**

我理解的学习能力是"学了能落地，落地了能深入"，不是掌握了多少技术栈。

我的每次技术扩展基本都有明确的问题触发——笔记项目需要持久化，才去学 Prisma 和 PostgreSQL；想提升 AI 检索质量，才去研究 pgvector 和非对称 Embedding；想让应用脱离浏览器运行，才踩完了 Electron 打包时二进制引擎丢失、符号链接悬空、子进程环境变量隔离三个坑。

目前在往 AI 应用开发方向深入，具体是把 RAG 链路做扎实——不只是接 API，而是把向量化策略、检索精度、可观测性这些工程细节都想清楚，能在线上通过日志快速判断检索效果并调参。

理解全链路让我在写前端代码时就知道数据怎么来、怎么存、怎么检索——不需要等后端告诉我哪个字段是什么意思。

## **核心能力三：细节把握**

我对细节的关注通常从用户体感出发，但落脚点在代码层面的完整性。

举两个例子：图片上传体验——Notion 里粘贴图片需要等待，我在做笔记项目时用 `URL.createObjectURL` 生成 Blob URL 实现秒级预览，再异步静默上传云端替换，用户感知不到任何等待，同时也解决了多图高清场景下 `FileReader` 转 Base64 阻塞主线程的问题。编辑器键盘行为——代码块里的 Enter 和 Tab 如果不拦截会触发浏览器默认行为破坏格式，我对这两个按键做了专门定制，确保行为符合开发者直觉。还有一些渲染时机我会适当加一些小动画来让使用过程更舒服

细节不是打磨，是产品可用性的下限。

## **开发时注意哪些难点**

> 我把开发难点分两层：**技术层面**和**判断层面**。

**技术层面**，我最关注**状态一致性**和**边界条件**。状态一致性的问题往往藏在异步链路里，比如 SSE 推送笔记数据的时序，稍有疏漏就是前端不知道数据何时到、编辑器白屏。边界条件则是极端场景，多图高清上传的主线程阻塞、批量请求的并发竞态，正常 demo 测不出来，生产环境很快会暴露。

**判断层面**，更难的是"做到什么程度"的取舍——什么时候牺牲一点性能换可维护性，什么时候先上简单方案再迭代。从 Quill 换到 Tiptap 的决定，就是整理出底层约束清单之后，判断长期维护成本超过了迁移成本才做的，不是跟着感觉走。这个判断力我还在培养，但已经开始有意识地去结构化地想它。

## **如何快速学习新技术**

我的习惯是先找锚点。新技术如果和已有知识有重叠，从重叠处切入会快很多——学 pgvector 时已经理解了 PostgreSQL 的 B-Tree 索引，再去看 HNSW 的近似图搜索逻辑就不是从零开始的。

如果是全新领域，我会先跑通一个最小 demo 把主链路走一遍，有了问题意识再去啃文档，比从头读文档效率高得多。

还有一个习惯是把踩过的坑记下来。Electron 打包那几个问题，每个都是踩坑之后才真正理解了运行时环境差异，这些认知很难从文档里直接获得。

## **意见不一致时**

我会先区分分歧是在目标层面还是方案层面。目标不一致需要拉齐优先级，适合引入更多人参与判断；方案不一致，我倾向于把两个方案的约束和权衡摆出来，用数据或者小范围验证来说话，而不是靠说服。

编辑器技术选型就是一个例子——从 Quill 换到 Tiptap，是在整理出 Quill Delta 模型的具体约束清单、评估了长期维护成本之后，才形成明确结论的。有了这个清单，讨论就变成了客观权衡，不是观点对撞。

## 开发难点

我觉得做一个项目的难是多维度的，最难的不是某个 Bug，拿我设计搭建个人AI助手来说吧，从 0 设计一个可扩展的 AI 插件架构。  
我要同时考虑：不同类型的 Skill 怎么解耦？RAG 链路怎么不影响对话主流程？怎么搭建整个前后端链路不至于出现数据孤岛？模型调用成本怎么控制？我的做法是"分而治之"：先把问题域拆开（Skill 插件、RAG 检索、流式协议、状态管理），每个子问题独立设计、独立验证，最后再组装。
