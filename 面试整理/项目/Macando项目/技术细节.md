## 基于 DOM 空间坐标映射实现 Y 轴点击深度的动态补行算法

> 之所以做这个，是想提高编辑器的自由度，实现可以在任意地方编辑，并且规范光标逃逸逻辑。

当用户点击的时候，通过事件对象拿到 `e.clinetY` 同时通过`getBoundingClientRect().bottom` 获得编辑器最后一行节点的内容。如果e.clientY 的值大于内容底部坐标，说明用户点击了下方的空白区域。通过两个差值除以默认行高，算出需要补多少个空行。从而插入空行并且完成格式清洗

## 解决ProseMirror机制的自动进行格式化和清洗

底层原理

### 问题解决

**采用**`Gatekeeper` **模式，引入**`isSettingContentRef`

- 当**系统代码**（如切换笔记）需要往编辑器里塞内容时（`isSettingContentRef.current = true`）。
    
- 这时 Tiptap 内部就算因为**清洗数据**触发了 `onUpdate`，也会被栏杆挡住（`if (isSettingContentRef.current) return;`），避免保存到数据库中。
    
- 通过`editor.commands.setContent(...)`等到真实内容渲染完毕后（借助 `setTimeout`）才执行（`isSettingContentRef.current = false`），完成数据库保存。
    
- 只有**用户真实敲击键盘**引发的 `onUpdate`，才能顺利通过栏杆，触发防抖保存。

### 本地 Ref 区域的作用

获取真实的 DOM 节点，直接获取屏幕上那个输入框或弹窗的 HTML 元素，用来控制焦点（`.focus()`）或者计算位置。

与`useState`不同，组件**完全不会重新渲染**，但这个值会被永久记住，直到组件被销毁。


## 响应式优化

> [!NOTE] 问题
> 随着项目的日常使用，已经不再局限于固定两种尺寸大小的适配，而是根据用户改变的尺寸大小进行灵活适配

因此需要CSS 容器查询（cqi）和 clamp() 函数的优势，让这些细节随着卡片尺寸的变大而“平滑呼吸”。

通过灵活通过**clamp() 函数**设置增长斜率 cpi 和 上限大小完成尺寸改变的丝滑变动

### 总结响应式优化的思路

首先从宏观层面，可以采用移动端、PC端尺寸分别做两种适配，比如一些组件的取舍和显示的位置。在实际开发中可以采用媒体查询、多用相对单位以及flex布局。

其次就是微观层面，可以采用 CSS 容器查询（cqi）和 clamp() 函数，对内部的组件根据不同大小进行平滑响应，完成响应式适配。


## 防御式编程

在真实的复杂网络环境中，依然有可能出现以下问题：

1. **多端并发**：用户昨天晚上同时在“手机浏览器”和“电脑浏览器”上打开了你的 Dashboard。到了午夜零点，手机和电脑**同时**触发了 `snapshotToday`，同时向你的后端发送了结算请求。
    
2. **网络重试**：用户在地铁里跨日了，网络很卡，浏览器自动把请求重发了两次。


如果没有（前端同日覆盖 + 后端基于 Map 强行去重），可能会导致服务器报 500 崩溃。

- 修改前端 `dashboardStore.ts` 的 `snapshotToday`不要无脑追加（push）数据，而是先检查数组里是不是已经有这一天了，如果有就覆盖，没有再追加
	
- 修改后端 `route.ts` 的 `PUT` 接口

我们要给后端加一层防弹衣，过滤掉前端可能传过来的 `null`，并做一次去重兜底。


## 基于临时 ID 的Base64 占位秒级预览与异步云端静默上传⽆感替换策略

> 这个功能是之前使用 Notion 的时候想要解决的一个痛点，因为Notion的图片就是需要用户等待才能完成图片的显示。因此基于这个痛点我主要解决了两个问题，**秒级占位**和**多图主线程阻塞**问题

### 秒级占位

用户粘贴进图片的时候，首先通过`FileReader`转成Base64占位符实现页面预览。

每当成功预览一张图片，我就会生成一个随机ID，完成Map字典的文件ID映射，然后静默上传到Cloudinary API中，将URL地址替换到对应占位编码存入本地数据库，实现大文件图片与本地存储架构分离

### 多图线程阻塞

后续考虑到一些极端情况，比如多图超高清图造成的**主线程阻塞问题**可以采用 `URL.createObjectURL(file)`这个原生 API 来替代 `FileReader` 转 Base64。

它不会真正读取文件内容，而是直接在内存中生成一个指向本地文件的 Blob URL，几乎是零延迟且内存占用极低。

当图片异步上传完成后，我们再把这个临时 URL 替换为云端 URL，并在合适的时机调用 `useEffect` 通过 `URL.revokeObjectURL()` 释放内存


## 基于 Prisma 实现双向链接系统，支持差量同步与反向引用查询，并集成 D3 力导向知识图谱可视化

> [!NOTE] 目的
> 为了打造高效的笔记模块，以及更好地结合导航Tab栏使用。以及为后续知识图谱的可视化打造，从而设计了一个双向链接系统。这个功能涉及到一些后端架构逻辑以及前端的技巧。

### 后端逻辑

后端提取节点进行字段提取入库。存入单独的一项由 `sourceId` 和 `targetId` 的表。来展示链接关系。从而支持差量同步和反向引用查询。最后通过这张表为后续的知识图谱搭建奠定基础

### 前端逻辑

通过`Suggestion`插件，定制对应钩子，比如识别字符并触发钩子，完成组件的创建、检索、销毁。然后搭配 `command()`方法插入属性为`type`和`attrs`的结构化节点。但是可能由于`ProseMirror`清洗机制，之前 command 操作先删除识别字符再插入结构，导致了当我选中需要链接的笔记的时候格式会被清洗掉，从而导致刷新页面插入的笔记消失的问题。因此我需要插入一个无空格的空字符来规避掉清洗机制。算是一个优化策略


## 采用继承类的方式完成复杂功能定制以及序列化和反序列化解决Quill底层Delta模型指针冲突问题

> [!NOTE] 说辞
> 这个源自之前的技术选型，最早我采用的Quill编辑器，底层模型的**复杂对象会有指针冲突的问题**。比如插入评论这项功能，因为涉及到内容和时间戳的对象，所以就会出现上述问题。因此我通过将时间戳、内容绑定到新创建的HTML属性以及后续读取属性。

- 存的时候，通过把对象转成 **JSON 字符串**从而将数据存在 HTML 标签的 `data-`属性上。
    
- 读的时候，把 HTML 标签上的属性抠下来，拼成 **JSON 字符串** 还给 Quill，让Quill处理 String 。全程用 String 交接，完美绕过 Bug。

后续的话可能因为底层不够成熟以及相关生态不够完善，我最终经过技术升级换成了更适配React的TipTap编辑器，这各部分让我知道事前选型的重要性
