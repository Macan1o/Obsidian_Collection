## 工作流编译器怎么测？

### 编译器的两层验证 


测试层面，`test_compiler.py` 覆盖了：Handler 注册完整性（恰好 5 种节点类型）、编译后节点类型与 JSON 一致性、虚拟 start 节点注入、边的 source/target/when 对齐、happy path 从 start 到 end、check 失败后路由到 human_gate。

另外还有 `test_workflow_projection.py`（编译器状态投影到 ClutchState）、`test_workflow_handoff.py`（节点间数据传递）、`test_workflow_cancel.py`（取消流程）、`test_workflow_step_failure.py`（步骤失败）、`test_flow_refine.py`（流程精化）。



> [!NOTE]
> 测试的目标，一是**保证这份 JSON 合法、图连得通**（编译前把关），二是**保证编译出来的图忠实于原图、并且真能按预期执行**（编译后验证）。

#### 编译前的验证我们做了两层

> 结构层用 JSON Schema 做静态校验，Schema 文件就是我们的契约，它规定了必须有 

- `id / name / version / nodes / edges` 这些字段
	
- 节点的 `type` 只能是五种枚举值——`start / agent_task / check / human_gate / end`
	
- `agent_task` 必须带 `label / agent / instruction`
	
- 边必须带 `id / source / target`
	
- 条件分支 `when` 只能取 `passed / failed / approve / reject / retry` 这些。

> 但此时只能表达字段正确，表达不了图是否能跑通，因此我增加了第二层：图结构校验

从虚拟的 `start` 节点做 BFS 遍历，检查三件事——有没有 `end` 节点、有没有从 `start` 出发的边、有没有从 `start` 永远走不到的孤立节点。构成完整的编译前把关。

## E2E 测试怎么覆盖 HITL 流程（需要人工交互的场景）？「<font color="#b7dde8">了解即可</font>」

> [!NOTE]
> 有 API 级和桌面端两级 E2E。各自排查对应应用场景的bug。

### 问题解决核心

```
真实用户在前端点 "Approve" 按钮

   → 前端发请求：POST /api/runs/{run_id}/human-decision  {decision:"approve"}
   → 落点：services/orchestrator/src/routes/chat.py:329  human_decision_http()
   → 调用 _apply_human_decision(run_id, "approve")
   → 恢复被 interrupt 的 LangGraph，从 n3 走 approve 分支 → end
```

> API 级是 `mvp-closed-loop.spec.ts`

```
npx playwright test mvp-closed-loop.spec.ts

   → Playwright 加载 test，拿到 request 夹具（只发 HTTP，不开浏览器）
   → ① POST /api/workspace {path: 临时目录}  → 200，授权工作区
   → ② POST /api/runs/start {workflow_id:'video-production', instruction:'e2e mvp'}
        落点：后端 start 接口 → begin_workflow → 跑图
        n2(check) 按 e2e 设计"失败" → 路由到 n3(human_gate) → 图被 interrupt
        返回 status = 'awaiting_human'            ←【结果：自动停在人工闸门】
   → expect(started.status).toBe('awaiting_human')  → 命中（过）
   → ③ POST /api/runs/{run_id}/human-decision {decision:'approve'}
        落点：human_decision_http → _apply_human_decision → 恢复图，n3 走 approve → end
        返回 status = 'passed'                    ←【结果：人工批准后跑到完成】
   → expect(finalState.status).toBe('passed')  → 命中（过）
   → 用例 PASSED ✅ → Playwright 汇总，退出码 0        【完成】
```

- 它能证明"接口把决策正确转给了编译器、返回状态对"。
	
- 但它**不开真实窗口**。如果桌面端"工作流触发"按钮的 `data-testid` 改了、点击 handler 崩了、菜单不渲染工作流项——HTTP 测试**发现不了**，因为压根没走 UI。
	
- 结论：接口对 ≠ 用户点得动。



> 桌面端是 `acceptance.spec.ts` 的 F1 测试

```
npx playwright test acceptance.spec.ts -g "F1"

   → 拿到 tauriPage（一个真实桌面窗口页面对象）
   → prepareChatTest：等 sidecar 健康 + 挂控制台守卫（监控页面报错）
   → authorizeSandboxWorkspace → startNewChat（开新会话）
   → page.click('[data-testid="footer-workflow-trigger"]')   → 真实点击"工作流触发"
   → 等菜单出现 → page.click('footer-workflow-item-{id}')     → 选具体工作流
   → sendChatMessage(启动指令)   → 真发一条消息触发工作流
   → waitForWorkflowRunning       → 等"运行中"
   → waitForWorkflowComplete(超时=timeout_minutes)   → 等跑到终态
        落点：后端把这条 demo 工作流一路执行到终态（不卡闸门，直接跑完）
   → 断言 result.status ∈ {passed, idle}  且  messageCount >= 6
   → 用例 PASSED ✅ → 汇总
```

- 它能证明"用户真能点按钮把工作流跑完"。
	
- 但它**慢、贵、易抖**：要真构建桌面应用、起 sidecar、甚至可能依赖本地模型（看文件里到处是 `test.skip(... 没有本地模型)`）。每提交都跑它不现实；而且一旦红了，你只知道"UI 层面挂了"，**很难定位到底是逻辑错、接口错、还是按钮错**——因为三层被它一个人扛了。
	
- 结论：全靠它，反馈慢、定位难。


后端还有 `test_human_gate.py` 调函数

```
pytest tests/test_human_gate.py -v
   → 模块加载：load_and_validate_workflow('video-production') 准备好图
   → 逐条执行 4 个 test_*（彼此独立，每条自己造 state）

   公共前奏（4 条都先走这段）：
       state = initial_compiler_state(run_id)
       state['check_result'] = 'failed'        ← 注入"检查没过"
       begin_workflow(图, run_id, initial_state=state)
           落点：compiler.begin_workflow → 跑图 → n2 failed → 停 n3(awaiting_human)

   ① test_failed_check_interrupts_before_human_gate
        → 断言 status='awaiting_human'、active_node_id='n3'、active_agent='Supervisor'
        → PASSED（验证"检查失败触发中断"）

   ② test_human_decision_approve_resumes_to_end
        → resume_workflow(session, run_id, 'approve')
            落点：resume → n3 approve 分支 → end
        → 断言 active_node_id='end'、status='passed'、human_decision='approve'
        → PASSED（验证"approve 恢复到 end"）

   ③ test_approve_clears_stale_check_result_before_resume   （回归 #52）
        → resume_workflow(session, run_id, 'approve') 后
        → session.compiled.get_state().values 读快照
        → 断言 not(human_decision) —— 决策被消费、无陈旧残留
        → PASSED（验证"approve 清除陈旧 check_result"，防 #52 老 bug 复发）

   ④ test_human_decision_retry_routes_back_to_builder
        → resume_workflow(session, run_id, 'retry')
            落点：resume → n3 retry 分支 → 回 n1(builder) 重做 → 再检查 pass → end
        → 断言 active_node_id='end'、status='passed'、human_decision='retry'
        → PASSED（验证"retry 路由回 builder"）

   → 全部跑完，pytest 汇总（如 "4 passed"）         【完成】
```

- 它能证明"approve 逻辑对、retry 路由对、#52 残留清了"。
	
- 但它**完全绕过 HTTP 和 UI**。如果有人把 `/api/runs/{id}/human-decision` 这个路由写错了、或者返回字段名拼错，后端单测**一片绿**，因为根本没经过那层。
	
- 结论：逻辑对 ≠ 接口对。
