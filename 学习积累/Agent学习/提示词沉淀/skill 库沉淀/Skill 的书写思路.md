## 模块 1:YAML frontmatter — 决定能不能被触发

| 要素               | 说明                  |
| ---------------- | ------------------- |
| `name`           | 用 kebab-case,和目录名一致 |
| `description` 开头 | 一句话说清"什么场景用"        |
| `description` 中段 | 列出隐式触发的关键词和语言/框架名   |
| `description` 末段 | 用引号包住用户可能的原话        |

description中建议采用反向声明触发边界的写法,能大幅提升隐式触发的命中率。例如：

	即使用户没点名开发,只要任务涉及代码文件、函数/类/接口、Java/Spring...也应触发

## 模块 2:定位与边界 — 决定 skill 不会跑偏

提前声明做什么和不做什么来限制 Agent 的执行边界



## 模块 3:分阶段执行流程 — 决定产出质量稳定

> 清晰的阶段划分是skill 和普通 prompt 的最大区别

| Skill                    | 阶段划分                                                                            | 核心思想         |
| ------------------------ | ------------------------------------------------------------------------------- | ------------ |
| `ai-pair-programmer`     | 建立上下文 → 精准澄清 → 设计改动 → 实现代码 → 验证收尾                                               | 先理解再动手       |
| `code-tutor`             | 鸟瞰层 → 业务层 → 模块层 → 代码层                                                           | 先全局后局部       |
| `writing-tech-tutorials` | Phase 0 探测 → Phase 1 澄清 → Phase 2 spec → Phase 3 plan → Phase 4 实施 → Phase 5 钩子 | spec→plan→实施 |
#### 提升关键

- 每个阶段有明确的输入和输出
	
- 阶段之间有"门禁"(上一步不通过不进下一步)
	
- 第一步永远是"建立上下文/探测",不是直接动手

> 还可以加入`HARD-GATE` 某个阶段用户不批准就回到某个阶段重写


## 模块 4:硬约束 / 规范 — 决定产出有底线

> 增加必须遵守的硬约束，是产出质量的保底机制

- <font color="#b7dde8">输出格式约束</font>
	
- <font color="#b7dde8">行为约束</font><font color="#b7dde8">「例如」</font>
	- 坚持 KISS、复用优先、渐进式修改。新增抽象必须解决真实复杂度，而不是让代码看起来更"高级"。
		
	- 项目现状不一定是最佳实践。发现坏味道时，给出能兼容当前系统的渐进方案，不顺手大改无关范围。
		
	- 不要为了流程感机械输出长篇模板。把信息压缩到用户做决定或理解结果真正需要的程度。
	
- <font color="#b7dde8">量化阈值</font><font color="#b7dde8">「关键」</font>

> 量化阈值是最强的约束——Agent 可以用 grep 自查是否达标,不达标就补,最多 3 轮


## 模块 5:反模式 — 决定 Agent 不会犯常见错误

> 通过反模式提前将 Ai容易犯的错误给堵住

- 每条反模式用 ❌ 或具体描述开头,让 Agent 一眼识别
	
- 反模式来自真实踩坑,不是凭空想象
	
- 配合"命中后怎么回退"的可操作建议,不只是说"别这么做"

例如：

	"流水账代码"指把多个业务步骤按时间顺序堆在一个方法里，缺少职责分层、语义抽取和变化点隔离。它短期能跑，长期难测、难改、难定位。


## 模块 6:references/ 子目录 — 决定 SKILL.md 不会臃肿

> 把详细规范从 SKILL.md 里分离出去,放到 `references/` 子目录。主文件只保留流程和加载指令

- SKILL.md 保持简短,Agent 加载快,核心流程一目了然
	
- 详细规范按需加载,不是每次都全读
	
- references 可以独立迭代,不影响主流程

## Skill 设计的五项原则

### 原则 1:先理解,再动手

	强制建立事实基础,是防止幻觉的根本手段。

### 原则 2:能从代码推断的不问用户

	能从代码、文档或配置推断的问题不要问用户。只在缺少业务规则、边界条件、产品选择或风险确认时提问。

### 原则 3:输出有约定,不自由发挥

	约定输出格式 = 约定产出质量  防止 Agent 每次输出都不一样

### 原则 4:有完成判据,不假装完成

	完成判据强制 Agent 结合实际汇报,没跑的测试要说没跑

### 原则 5:给用户下一步选项,不让人迷失

	给选项让协作能持续下去

## Agent Skill 三层测试体系

### Skill 加载精度（工具选择准确率）

- **Precision（精确率）**：该调用的 Skill 有没有正确匹配，不误选无关工具；
	
- **Recall（召回率）**：用户需求需要这个工具时，有没有成功识别并调用；
	
- **Forbidden（禁调用校验）**：明确不该使用该工具的场景，会不会错误加载（比如权限禁止、场景不匹配时乱调用）。简单说：检查「Agent 知不知道什么时候该用、什么时候不能用某个工具」。

#### 验证方法

> 批量输入各种用户查询，拦截底层函数 `load_skill()` 的调用记录，对比**预期应该加载的工具**和**实际触发加载的工具**，统计精确率、召回率、误触发次数。

### 渐进式加载（工具加载流程完整性）

校验**工具加载后的附属资源逻辑**验证加载 Skill 时，配套文件会不会正常读取、有没有漏读 / 重复读 / 读取失败。按需分批加载工具资源，避免一次性加载全部文件造成性能浪费。

#### 验证方法

> 监控程序文件读取行为，日志统计加载 Skill 时的文件 IO 操作，核对是否按设计读取对应附属资源，有无异常读写。

### 端到端任务完成（最终业务效果）

看**最终结果**是否能真正帮用户把任务完整做完、解决需求。

#### 验证方法

- 完整跑一遍**Agent 全流程循环**（用户提问→选工具→加载工具→执行工具→整理结果回复用户）；
	
- 再用 LLM 充当评审员（LLM judge），根据预设打分标准（rubric 评分细则），给最终任务完成效果打分，量化 Agent 真实可用性。
